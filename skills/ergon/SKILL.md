# ergon: open work, sized by which model can do it

One markdown file per task and per epic. Each epic is a folder, `<state>/epics/E-NNN-slug/`, holding its brief (`EPIC.md`) and all of its tasks (`T-NNN-slug.md`), done and dropped ones included. Tasks with no epic live in `<state>/items/`. `<state>` is `state` in the project's `.ergon.toml` (default `tasks`). Frontmatter is the state; the body is the brief. The `ergon` CLI reads and writes it: run `ergon -h`.

The `epic:` field decides the folder. `ergon set T-NNN epic=E-NNN` moves the file (`epic=` moves it back to `items/`). After a hand edit, `check` fails until `ergon tidy` re-files it. `ergon tidy` also removes a leftover `<worktrees>/E-NNN` checkout (detached, or its branch gone) once its epic is no longer open, but only if `git status --porcelain` there is empty and you aren't inside it; otherwise it lists it with the reason. Task worktrees and open epics' worktrees are never touched. Other files in an epic's folder, such as design notes, are ignored by the tracker.

**Task state is local.** `items/`, `epics/` and `runs/` are gitignored (`ergon init` adds the lines). Git keeps the record of what was done: every commit for a task cites its ID (`… (T-128)`), and an epic's merge commit lists its goal, each task, and the commits that cite it. Anything that should outlive your machine goes in a commit message, not in a task file.

**Exception: shared mode.** With `[shared]` in `.ergon.toml` the task files are a worktree of an orphan state branch (`ergon-state`) that a team keeps in step with `ergon sync`. Everything above still holds on each machine, and in this mode the state branch is the one thing ergon pushes (never code). Rules for agents:
- **Never run `ergon sync`, and never push.** Only a human syncs, plus dispatch for its claims. `sync` and git writes in the state worktree are refused in an agent shell and on a `task/` branch. Your `ergon new` / `set` is committed locally on the state branch and goes out at the human's next sync.
- **IDs of unpublished tasks can change.** If a teammate took the same ID, sync renumbers the local task that was never published (and its `depends:` / `source:` links). Approving or starting a task syncs it first, so an ID cited in a commit never changes. Don't cite a `proposed` task's ID anywhere durable.
- **Approvals are signed.** A human's `approve` makes an SSH-signed commit whose trailer names the brief's digest. A task counts as approved only if a key in `.ergon/approvers` (read from the remote's trunk) signed its current brief, so editing an approved brief un-approves it, and writing `status: ready` or an `approved:` stamp yourself does nothing. `next`, `check` and dispatch verify it.
- **Two-person rule.** A task matching a `[[two_person]]` rule needs two different approvers. After the first it stays `proposed` with a Note (`1 of 2`); `ergon review` shows who is still needed.
- **Concurrent status moves lose to the remote.** If someone else moved the task first, your move is dropped and a Note says so. Dispatch claims each breakdown the same way, with a `breakdown: <user>@<host> until <deadline> (<nonce>)` field it pushes on the epic before the agent launches and takes off when the breakdown ends. Another clone's dispatch that sees a live claim doesn't break that epic down and says another dispatcher holds it; a claim that can't be pushed launches nothing; a claim left by a dispatcher that died lapses at its deadline (its `--timeout` plus 15 minutes). Never write or remove `breakdown:` yourself. A task dispatch holds at `review` is accepted only from the clone that holds its branch (`held: user@host`).

**Signed approvals in local mode (`[signing]`).** A project can opt in to shared mode's signed approvals without sharing anything. With `[signing]` in `.ergon.toml`, a human's `ergon approve` (and `a` in `review -i`) signs `<ID> sha256:<digest>` for each task or epic brief it approves with `ssh-keygen -Y sign` and their `user.signingkey`, into `<state>/approvals/`. A task or an open epic counts as approved only if a signature from a key in the approvers file (`[signing] approvers`, default `.ergon/approvers`, an `allowed_signers` file read from the trunk as committed, never the working tree) covers its current brief digest. So, as in shared mode: writing `status: ready` or an `approved:` stamp yourself does nothing, editing an approved brief un-approves it, and a signature by an unlisted key doesn't count. `next` leaves such a task out, dispatch skips it, the commit-msg hook refuses a commit citing it, and `check` says why. Follow-ups stay `proposed` (no approval by inheritance). It fails closed: no `ssh-keygen`, no approvers file, or a bad signature means nothing is approved. The approvers file is a gate file: never change it, never write in `<state>/approvals/`, and never touch `[signing]` in `.ergon.toml` (once committed to the trunk, the trunk's copy is the one read anyway). The human's key must need a touch or a confirmation (a hardware key, `ssh-add -c`), so that an agent in their shell can't sign; a key unlocked in an agent with no prompt makes the signature prove nothing.

The project's own rules (tier signals that are specific to it, hosts that need a human, what workers must never touch) live in its `CLAUDE.md`/`AGENTS.md` and in `worker_rules` (`ergon rules` prints them). Read them before working a task.

## The one rule: humans approve, agents execute

- Every task an agent creates starts `status: proposed`. That includes tasks from breaking down an epic.
- **Epics are gated the same way.** Agents may propose epics: `ergon new epic` writes `status: proposed`. Only a human's `ergon approve E-NNN` approves the brief (Goal / Out of scope / Constraints), stamps `approved:` and opens the epic. Until then `next`, `start`, `set … status=doing` and dispatch leave its tasks alone, even approved ones. Once it's open, `ergon approve E-NNN` approves its proposed tasks, as before. To turn a brief down instead, a human runs `ergon reject E-NNN --reason R` on the proposed epic: it becomes `dropped`, the reason kept in its file and a `rejected` history row (in shared mode a signed state commit with an `Ergon-Reject: E-NNN` trailer), and its tasks are never offered or started. Like approving, that acts on the brief alone and says so: the epic's proposed tasks stay proposed until the human names the dropped epic again, which drops them. On an epic that isn't proposed, `ergon reject E-NNN` drops its proposed tasks, as before. In shared mode the epic's approval is signed over its brief's digest like a task's, so editing an approved Goal un-approves the epic: its tasks stop being offered, `check` fails, and a human approves it again. Epics from before this rule (open or done with no `approved:`) count as approved in local mode without `[signing]` only. In shared mode, and with `[signing]`, an open epic counts only if its signed approval verifies, stamp or no stamp, so an old unstamped one (or one a clone without the guard pushed) holds its tasks back and fails `check` until a human runs `ergon approve E-NNN` on it, which approves its brief again. `set` won't move an epic into or out of `proposed`, and the guard refuses agent edits of an epic file's `status:` or `approved:`, and a new `EPIC.md` that isn't `proposed`.
- Only a human moves a task to `ready`: either `ergon approve <ID|E-ID>` from their own terminal (it refuses inside agent shells and asks for confirmation), or by hand-editing `status: ready` + `approved: <name> <date>` (which counts for nothing in shared mode or with `[signing]`, where only a signed approval does).
- **One exception: follow-ups that aren't features.** A FOUND line from a dispatched worker (Dispatch below) is approved by inheritance from the task that found it, and dispatch files it straight to `ready`, only if all six of these hold when it is filed:
  1. its `category:` is `bugfix`, `refactor` or `chore` (empty or unknown counts as `feature`);
  2. its tier isn't `human`;
  3. its `touches:` is non-empty and no entry falls under a `[[protect]]` rule, whatever that rule's `min_tier`;
  4. its depth is at most `follow_up_depth` (`.ergon.toml`, default 3; `0` turns this off). Depth is the length of its `source:` chain of auto-approved tasks back to a human-approved root: a follow-up of a human-approved task is depth 1, a follow-up of that one depth 2;
  5. approvals aren't signed. In shared mode, or with `[signing]`, an approval is a signature over one task's brief, and a parent's signature can't vouch for a task that didn't exist when it was signed, so follow-ups stay `proposed` there;
  6. its `## Done when` isn't empty: a follow-up with nothing to work or review against waits for a human (its Notes line says `ergon fill <ID>` writes one).

  On top of these, the run that found it must have finished `done` (or held for `accept`), so a reviewer, where one is set, passed what it reported; a blocked, vetoed or asking run files every FOUND line `proposed`. A feature always waits for a human. The stamp says where the approval came from: `approved: auto bugfix follow-up of T-095 (root T-095, Pavel Sinelnikov 2026-11-17)`, and an `approved` history row records `by: auto` with `parent`, `root` and `depth`. `ergon check` holds an `auto` stamp to the six conditions for as long as the task is open. It also checks that the stamp names the task's `source:` and `category:`, and that its parent is validly approved itself (human, or `auto` all the way up). It reports a task that fails any of these, so a hand-written `auto` stamp on a feature fails `check`; dispatch skips such a task, and the commit-msg hook refuses a commit citing it. The hook also refuses a commit citing a task whose epic's brief isn't approved (`proposed`, dropped, or in shared mode open without a signed approval that verifies). The guard and `ergon set` refuse an agent's change to `category:` or `touches:` of an auto-approved task, so a follow-up can't be relabelled or widened after it was approved. To take such a task over, a human edits it back to `proposed` (its `status:` and `approved:`) and approves it, or drops it.
- **Agents never write `approved:`, never set `status: ready` on a proposed task, and never work a task that isn't `ready`.** `ergon set` enforces this, and `ergon check` fails on any task past `proposed` that has no stamp. The plugin's PreToolUse hook (`ergon hook guard`) also refuses agent edits that change a task file's `status:`, `approved:`, `asking:`, `answered:` or `pin:`, or the `Chosen:` line under its `## Options` (adding, changing or removing it), or the `touches:` or `tier:` of a task past `proposed` (part of what a human approved: changing either is a re-plan, so a dispatched worker ends `RESULT: blocked — re-plan: <why>`; `ergon set` refuses both from an agent shell or a `task/` branch too), shell writes to task files, any write to `<state>/runs/` (`history.jsonl` and the run logs), `approve`/`reject`/`close`/`accept`/`answer`/`pin`/`choose`/`review -i`, and touching `CLAUDECODE`/`AI_AGENT`.
  Its Stop hook runs `check` once before a session ends. All of it is a speed bump, not security. Bypassing it breaks this rule. (The guard refuses edits to `pin:` as well.)
- **Pins are a human's too.** `ergon pin <ID> first|last|clear` (human only: it refuses inside agent shells) sets or clears the `pin:` field, which puts a task first or last in the order whatever its score (see Priority). It reorders only, so it asks for no confirmation.
- **Humans accept output too, where the project asks for it.** A task marked for acceptance (its own `accept: yes`, or an `[[accept]]` rule in `.ergon.toml` matching its tier or `touches:`) stops at `status: review` when dispatch would land it: verify and any reviewer agent have passed, the branch and worktree are kept, nothing is merged. Only a human moves it on: `ergon accept <ID|E-ID>` lands it (the merge dispatch would have done, then the epic closes if that was its last task), and `ergon reject <ID> --reason R` sends it back to `ready` with the reason in its Notes. Both refuse inside agent shells and ask for confirmation, like `approve`. **Agents never move a task out of `review`, never take `accept:` off a task, and never run `accept`.** `set` refuses the move, and the guard refuses the file edits and the command.
- **Answers are a human's too.** `ergon answer <ID> "<text>"` (or `ergon answer <ID>` to pick from the worker's options) steers what an approved task does, so it is gated like `approve`: it refuses inside agent shells, asks for confirmation, and the guard refuses it from a tool call. It is never to be exposed over HTTP. An answer only steers: it never changes `approved:`, tier, `touches:` or `accept:`. A question that needs one of those is a re-plan. Edit the task yourself, or close it and file a new one.
- **Choices are a human's too.** When an agent proposes a feature (category `feature`, or empty), it never files one fixed approach: it gives a crux and 2 to 4 peer alternatives, none recommended, as the task's `## Options` section (`ergon new task … --crux "<what the choice turns on>" --option "<lens>: <approach> | <optimizes for> | <gives up> | <regret if>" --option "…"`, one option per lens: minimal, durable, operator, risk, defer; in an agent shell `new task` refuses a feature with no crux or malformed options and names each problem). A bugfix, refactor or chore needs none, and outside an agent shell plain `--option "<approach>"` text writes an unmarked numbered list. A human picks lens options by name, one lens or several to combine them (`ergon choose T-NNN operator minimal` writes `Chosen: minimal + operator by <name> <date>`, lenses in lens order: the worker builds what the named options share and takes each one's distinct part), a numbered list by exactly one number (`ergon choose T-NNN <N>`), or `ergon choose T-NNN --own "<text>"` for an approach of their own (`ergon choose T-NNN` alone offers the options and takes lens names, a number or their own words, as `c` in `review -i` does). It refuses an unknown or repeated lens, a lens on a numbered list and a number on lens options. It is gated like `approve`: it refuses inside agent shells, prints the options and asks for confirmation, and the guard refuses it from a tool call. It works on a `proposed` task with an `## Options` section only. It writes (or replaces) `Chosen: <lens>[ + <lens> ...] by <name> <date>`, `Chosen: <N> by <name> <date>` or `Chosen: own by <name> <date> — <text>` as the section's first line and records a `chosen` history row (`option`, `text`, and for a lens choice `options`, the list of lenses). `ergon approve` and `review -i`'s approve refuse a task whose `## Options` has no `Chosen:` line and name `ergon choose`; a task with no `## Options` section is approved as before. `ergon check` fails a task past `proposed` whose options have no choice (so a hand-written `status: ready` can't skip it), and a malformed section: fewer than 2 numbered items, a lens-format section that breaks its rules (see the task file format), or a `Chosen:` line that doesn't read, names a number not in the list, or names a lens the section lacks (or one twice). The section, choice included, is in the brief digest, so in shared mode the signed approval covers the choice. A choice steers only: it never changes `tier`, `touches:`, `accept:` or `approved:`. If the chosen option needs a different tier or touches, the human edits those before approving.
- Reviewing a long queue: `ergon review -i [--epic E-00N] [--tier T]` walks it one item at a time, in three groups. Proposed work, each epic brief due for approval just before its tasks (a proposed epic, or in shared mode an open one whose stamp doesn't verify): for a brief it prints the Goal, Out of scope and Constraints and offers approve / reject (a proposed brief only: drops it as `ergon reject E-NNN` does, its tasks stay proposed) / open in `$EDITOR` / skip, where approving does what `ergon approve E-NNN` does for a brief (signed in shared mode; the epic opens and its tasks stay `proposed`); for a task, approve / reject / change tier / open in `$EDITOR` / skip, plus `c` to choose for a task with options, which does what `ergon choose` does (approve is refused until it has a choice); rejecting, brief or task, asks for the reason — there is no dropping without one. `ergon review` lists proposed tasks with options and no choice under AWAITING A CHOICE, each with its options, instead of with the tasks to approve. `--tier` leaves briefs out (they have none); `--epic` keeps that epic's brief. Tasks awaiting an answer (`asking`): it prints the worker's questions and offers `a` to answer, which does what `ergon answer` does (same confirmation, same Notes line, the task goes `ready`; it lands at once), or skip. Tasks held on a review veto: `p` to save the finding as a policy, or skip. Human only, like `approve`.
- Pick work with `ergon next --tier <your tier>`. Take only tasks at your tier or below. To run many at once, see Dispatch below.

## Tiers: the cheapest one that will get it right

| Tier | Give it | Signals |
|---|---|---|
| `haiku` | Mechanical and fully specified | One file or a few. The exact change is already written in the task. Checking it is trivial (a grep, a lint, a doc row). No judgment about behavior |
| `sonnet` | Scoped engineering | One app or subsystem, clear acceptance criteria, has to read code and run tests. Most bug fixes, doc-drift passes, config fixes |
| `opus` | Cross-cutting, ambiguous, or security-sensitive | Spans subsystems or repos. Touches auth, signing, secrets or a stated invariant. Root cause unknown. Needs a design decision first |
| `human` | Things no model should or can do | Live production changes, third-party consoles, credentials, on-chain or legal actions, risk or policy calls |

A project can pin minimums with `[[protect]]` in `.ergon.toml` (`touches = ["server/auth/**", "prod-db"]`, `min_tier = "opus"` or `"human"`, optional `note`). `ergon check` fails any open task whose `touches:` match a pattern (fnmatch, also against parent directories) but whose tier is below the minimum. Done and dropped tasks are ignored.

When in doubt, go one tier up. Put the reason in `tier_why:` in one line. If a task has a human step and a code step, split it into two tasks and link them with `depends:`.

## Priority: what goes first

`ergon/priority.py` orders the open work. For each task:

`score = (cod + 25 × unblocks) / size`

- **`cod`**: cost of delay, 0-100, from the task's `cod:` field. A missing or unparseable value counts as the neutral 50, and out-of-range values are clamped.
- **`unblocks`**: how many open tasks depend on this one, directly or through a chain. Done and dropped tasks don't count.
- **`size`**: haiku 1, sonnet 3, opus 8, human 3.

Order: tasks pinned `first` go to the top, tasks pinned `last` to the bottom, and the rest sit between by score, highest first. Ties go to the cheaper tier, then the lower ID. `ergon next`, `dispatch` and the `ergon serve` board all use this order. `ergon show` prints the score and its parts.

`ergon grade [--all] [--epic E] [--per 4] [--model sonnet] [--budget USD] [--dry-run]` sets `cod:` by pairwise comparison (one `claude -p`, no tools). By default only stale tasks are graded: those with no `graded:` stamp, or whose stamp no longer matches the brief. `--all` regrades every open task. Grading writes only `cod:`, `cod_why:` and `graded:`. None of them is in the brief digest, so grading never un-approves a task and a signed approval still holds.

## Filling in thin briefs

Every task has a `category:` (feature, bugfix, refactor or chore; `ergon new --category`, `ergon set T-NNN category=…` on any status). It is outside the brief digest, so setting it never un-approves a task. The two fields that weaken a gate are the other way round: a task's `verify:` (it replaces the runtime gate, and `verify: true` passes anything) and `prove: no` (it skips the red-on-base proof). `ergon set` refuses `verify=` and `prove=no`, and the guard hook refuses an agent's file edit that adds, changes or removes `verify:` or sets `prove: no` (local mode has no digest to catch it), so a human writes them by editing the file, and both are in the brief digest, so writing one on an approved task un-approves it until a human approves it again. A harden task's `harden:` and `harden_layer:` are the same kind: a harden task skips the red-on-base proof and the layer picks the gate its own proof runs, so `set` refuses both (any value, clearing included), the guard hook refuses an agent's file edit that adds, changes or removes either, and both are in the digest (only when it names incidents). `suppress_ok:` (the files a task may add a suppression marker to, see the weakening check) is the same kind again: `set` refuses it, the guard refuses an agent's edit that adds, changes or removes it, and it is in the digest as a set (only when it names a file). A task with none of these keeps the digest it had before they counted, so existing signed approvals still verify. `ergon fill` writes a blank category on a task of any status, so one run backfills old tasks; `ergon stats` counts done tasks per category.

`ergon fill [ID|E-ID ...] [--epic E] [--model sonnet] [--budget USD] [--dry-run]` writes the parts a proposed brief left blank: What, Done when, `touches:`, and `tier` with `tier_why:` when nobody sized it (empty, or the placeholder a FOUND line or an import leaves). It runs one `claude -p` per batch of up to 8 tasks in the main checkout with Read, Grep and Glob only, so it can cite `file:line` and name real paths. It never replaces what's written and never edits a task past `proposed`. A tier below a matching `[[protect]]` minimum is raised to it. Each filled task gets a Notes line naming what was machine-written: read it before approving. Agents may run it, since it only proposes. The record goes to `<state>/runs/fill/`.

## Concept map (optional)

`depends:` and shared `touches:` say how tasks are linked by order and by file. A concept map links them by what they are about. `concepts = "concepts.toml"` in `.ergon.toml` names a TOML file in the repo that lists concerns, then components. Each is an array-of-tables entry with an `id`, so the map parses without `tomllib` (Python 3.9):

```toml
[[concern]]
id = "approval"
label = "Humans approve, agents execute"

[[component]]
id = "approval.guard"             # letters, digits, '.', '_' or '-'
concern = "approval"              # a [[concern]] id
files = ["ergon/gates.py", "hooks/*.json"]   # fnmatch patterns, like [[protect]]
terms = ["guard", "heredoc"]      # words a brief about it tends to use
fns = ["guard_reason"]            # optional: the functions that implement it
introduced_by = "T-136"           # optional: the task that creates it, or "none" (see Origins below)

[[ignore]]
id = "packaging"                  # same id rules as a component
files = ["ergon/__init__.py", "ergon/__main__.py"]   # fnmatch patterns no component needs to cover
label = "Package glue"            # optional
```

Don't write `[component."approval.guard"]`: the fallback parser has no quoted or dotted table names, and `check` refuses that shape on every Python. ergon's own map is `concepts.toml` in its repo.

A task's `concepts:` lists component ids. `ergon tag [ID|E-ID ...] [--all] [--model sonnet] [--budget USD] [--dry-run]` writes it: one `claude -p` with no tools per batch of up to 10 tasks picks from the map's ids, and any other id in the reply is dropped. A `tagged:` stamp (day and brief-hash prefix, like `graded:`) makes the tags stale once the brief changes or once they name a component the map no longer has. With no IDs, `tag` retags only stale tasks (any status but dropped, so done tasks are tagged too); `--all` retags every one, which is what to run after a big change to the map; named IDs are always retagged. Neither field is in the brief digest, so tagging never un-approves a task. Agents may run it. The record goes to `<state>/runs/tag/`.

`ergon related T-NNN` (read-only) prints, for a tagged task:
- open tasks that share a component with it, then open tasks that share only a concern;
- done tasks it builds on, ranked by component overlap (Jaccard), the top 5;
- the files changed by the commits on main that cite it, from one `git log --no-merges --name-only` per run. A `Merge T-/E-` landing subject cites nothing, and paths under the state dir are dropped (shared-mode state commits cite task IDs too);
- done tasks whose citing commits changed the same files, the top 5. Each shared file weighs log(tasks with citing commits ÷ tasks whose commits changed it), so a file nearly every task changes (README, SKILL.md, shared tests) counts for almost nothing; the score is the sum, ties go to more shared files, then ID order. Each row lists the shared files, rarest first;
- missing depends: a component it uses whose `introduced_by` task is still open (not done or dropped) and isn't in its `depends:` closure.

An untagged task gets the "run `ergon tag`" hint and the two file lists. Nothing is stored or cached: each run reads git again.

`/t/T-NNN` in `ergon serve` shows the same lists, except the two file lists (the page doesn't run git). `ergon check` fails a map that doesn't hold (a missing file, an unknown concern, a duplicate id, an `introduced_by` naming a missing task) and only warns on a missing depend, on tags the map lacks, on a dropped `introduced_by`, on uncovered files and on suggested origins. Coverage: the leading directory of every component `files` pattern that names one (`ergon/gates.py` gives `ergon/`, `agents` gives `agents/`) is a root, and every tracked file under a root (one `git ls-files`) must match some component's `files` or an `[[ignore]]` entry's, the way touches match `[[protect]]`. Each one that doesn't is a `warning:` naming it; add it to a component, or to `[[ignore]]` when it needs none. Files outside the roots aren't checked, and the check is skipped when git can't be run, the folder isn't a repo or the map doesn't hold. Warnings never fail `check` and the Stop hook doesn't show them. A missing depend is a lead, not a rule: add the depend if the task really needs that work first. By default scheduling ignores the map and dispatch holds tasks apart by shared `touches:` only; `hold_by = "component"` makes it want a shared component too (Dispatch, "Overlap").

Origins: `ergon related --origins` (read-only, writes nothing; agents may run it) suggests an `introduced_by` for each component that has none. For each tracked file the component's `files` match, it takes the commit that first added it (`git log --diff-filter=A --no-merges`, renames off) and the task IDs that commit cites. `Merge T-/E-` landing subjects cite nothing, and neither does a file a merge added. The suggestion is what the oldest citing commit cites, and each comes with its evidence, one `file -> commit -> tasks` line per file. A suggestion is a guess and needs a human's judgement. The first add is often a move or a package split, not the work that built the component: `ergon/gates.py` was first added by the package split T-023. Paste the right ones into the map. `introduced_by = "none"` rejects a wrong one for good. `ergon check` warns about each component that has a suggestion and neither value set, so suggestions keep showing until someone decides.

Function-level touches: an entry may name one function as `<path>/::<fn>` (e.g. `ergon/gates.py/::guard_reason`; one entry per function). The `/` before `::` is on purpose: every file-level rule (`[[protect]]`, `[[accept]]`, `[[evidence]]`, `[[two_person]]`, approval by inheritance) matches a touches entry by its `/`-separated leading parts, so the entry still falls under a rule naming `ergon/gates.py`; plain `ergon/gates.py::guard_reason` would not, so `check` fails it and `set` and dispatch refuse it. A function counts only when the concept map lists it (some component's `fns` has it and one of that component's `files` patterns matches the path); otherwise the entry is refused. Two tasks touching different functions of a file don't overlap; the same function, or a file-level touch of the file, does.

Without a `concepts` key, `tag` and `related` say so and nothing else changes.

## Lifecycle

```
proposed --(human approve)--> ready --> doing ------> done <--(human accept)--.
    \--(human reject)--> dropped ^ ^     |  \-> blocked -/                    |
                                 | |     |--(dispatch, if marked)--------> review
                                 | \-----|-------------(human reject)--------/
                                 |       |--(worker or reviewer stopped by the usage limit)--> blocked, limited: <reset> <step>
                                 |       |<-(first dispatch scan after the reset; no human)-------------/
                                 |       \--(worker: RESULT: asking)--> blocked, asking: <session>
                                 \-----(human answer; next dispatch resumes that session)----/
```

Agents move tasks through `ready → doing → done|blocked` with `ergon set T-012 status=doing`. Only dispatch moves a task into `review`, and only a human's `accept` or `reject` moves it out; `ergon review` lists those tasks under AWAITING ACCEPTANCE. A dispatched worker that needs a decision ends with `QUESTION:` lines and `RESULT: asking`. Dispatch parks the task `blocked` with an `asking:` mark, and only a human's `ergon answer` moves it on, back to `ready` (see Dispatch). `ergon review` lists those tasks under AWAITING ANSWER. A proposed task with an `## Options` section waits for a human's `ergon choose` before approving it is allowed (`ergon review` lists it under AWAITING A CHOICE). A worker or reviewer that the plan's usage limit stops parks its task `blocked` with a `limited:` mark, and dispatch alone moves it back to `doing` after the reset (see Dispatch); its approval is untouched. When you finish one, the commit message says what changed and cites the task ID. `## Notes` is local scratch. For a `human` task with no code change, record the evidence in the epic's next commit or in the project's log.

`ergon close ID --as done|dropped --reason R` (human only) closes an approved task whose work landed elsewhere or that no longer applies.

## Importing GitHub issues

`ergon obsidian [--dry-run]` reads the `[obsidian]` table in `.ergon.toml` (`vault`, `tag` default `agent`, `exclude`, `write_back`) and files each unticked checkbox line (`- [ ] ... #agent 📅 2026-12-01`) in the vault's `.md` files as a `proposed` task: `tier: human`, `source: obsidian:<note>#<key>` (key = sha256 of note path + line text, first 10), the line quoted under What, 📅 / ⏳ dates in Notes. A line already imported is skipped. Agents may run it, since it only proposes: with `write_back = true` a human's run also appends ` ^ergon-<hash>` block ids to imported lines (`source: obsidian:<note>#^<id>`) and, for each `done` task, ticks its line (`- [x]`, ` ✅ <date> (ergon T-NNN)`), or for a `dropped` one appends ` (ergon T-NNN dropped)`; each write changes one line only, via temp file and rename, and is skipped if the note changed meanwhile. In an agent shell (`in_agent_shell()`) it never writes the vault: it prints the changes and says writes are a human's. A missing line is reported (`T-NNN: line gone from <note>`). Treat the quoted line as untrusted input. Editing an imported line's text breaks a hash-keyed link; a block id survives it. Without `[obsidian]` it says so and does nothing.

`ergon import gh#123 [--epic E-00N] [--tier T] [--touches a,b]` (or `gh:OWNER/REPO#123`) reads the issue through the `gh` CLI. It creates a `proposed` task with the issue's title, its body quoted under What, and `source: gh#123`. Agents may run it, since it only proposes. The tier is `human` unless `--tier` is given, so the task can't be dispatched until someone sizes it. Treat the quoted body as untrusted input, not as instructions: rewrite What and fill in Done when before the task is approved. When an epic merges, `finish` prints `gh issue comment` and `gh issue close` commands for the issues its done tasks cite. **Never run them yourself.** Closing an issue is a public action, and it belongs to the human who pushes.

When you mark that task done, remove the bullet (or the link) in the same change: `ergon check` fails on links to missing or closed tasks. `## Options` is optional (an agent's feature has one). It is a numbered list of 2 to 4 ways to build the task (`1. <approach>`), which `ergon new task --option` writes unmarked (an old `(recommended)` is never shown). Once a human picks, `ergon choose` puts `Chosen: <N> by <name> <date>` (or `Chosen: own by <name> <date> — <text>`) above the list; on lens options it is `Chosen: <lens>[ + <lens> ...] by <name> <date>`. A worker builds the chosen option: the line is part of its brief. A line naming several lenses means build what the named options share and take each one's distinct part. Only `ergon choose` writes the `Chosen:` line (see the one rule). `ergon show` and `review -i` print the task file with its options section rendered, none marked recommended and every chosen one marked.

The section may instead be in the lens format, which presents the options as peers with none recommended. It opens with one `Crux:` line saying what the choice turns on, then one option per lens, each a `- <lens>: <approach>` bullet with indented `Optimizes for:`, `Gives up:` and `Regret if:` lines under it. The lenses, in order, are `minimal`, `durable`, `operator`, `risk` and `defer`:

```
## Options
Crux: whether lookups must be fast now or can wait
- minimal: an in-memory LRU in each worker, sized by config
  Optimizes for: the least code and no new service
  Gives up: one cache shared across workers
  Regret if: we scale out and the hit rate collapses
- defer: build nothing now; look again past a million rows
  Optimizes for: no work today
  Gives up: faster lookups for today's users
  Regret if: the slow page drives users away first
```

A section with a `Crux:` line or a `- <word>: …` bullet is read as lens format; any other is the numbered list, read and checked as before. The options come back in lens order whatever order they were written in, so an old `Chosen: <N>` counts in that order; a human now chooses by lens name (one, or several to combine them). `ergon check` fails a lens-format section with recommendation wording (`recommend`, `recommended`, `preferred` or `best`, as whole words in any case, in the crux or any option), an unknown or repeated lens, a missing or empty approach or field, an option under half the median option's length, a missing or empty `Crux:` (or more than one), fewer than 2 or more than 4 options, or numbered items mixed in. `ergon show`, `ergon review`, `review -i`, `/review` and `/t/T-NNN` print the crux and each option's fields in lens order, mark every chosen lens (a combination marks each) and none recommended; `show` and `review -i` print the file with its `## Options` section replaced by that rendering.

Frontmatter is a small YAML subset: `key: value` lines, quoted scalars (`status: "ready"` reads as `ready`), and lists in either style: flow (`depends: [T-010]`) or block (`depends:` then `- T-010` lines, as Obsidian's Properties editor writes them). Ergon reads both and always writes flow lists and bare scalars. No nested maps, no multi-line strings. `ergon check` fails a line it can't read, naming the file and line.

The body sections stay short. Cite `file:line`. Don't restate the spec.

## Epic or task?

**A task is one change or one human action.** It has one tier, one Done when that can be checked, and a branch that can land by itself: dispatch merges each task branch into its base as soon as verify and review pass. If a piece of work needs two tiers (a human step and a code step, say), it is two tasks linked with `depends:`. If one worker can't finish it in one session, or its Done when lists unrelated outcomes, split it.

**An epic is a goal that takes several tasks that should land together.** Its tasks merge into the epic branch, and that branch reaches the trunk only when every task is done or dropped. Make an epic when:
- a half-done state shouldn't reach the trunk (a schema change and the code that reads it, a feature that is useless until its last piece lands), or
- the work needs a Goal, Out of scope or Constraints that every task's worker should respect, or
- you want to approve, track and later read about the work as one thing (`ergon approve E-NNN`, the merge message, the journal entry).

**A task with no epic** (in `items/`) is a change that makes sense on the trunk by itself: a bug fix, a doc-drift pass, a config fix. Several such tasks that only share a theme don't need an epic. Grouping them would hold every fix back until the last one lands.

The quick test: if the work fits one tier and one Done when, and could merge to the trunk alone, it's a task. If it takes several of those that only make sense together, it's an epic. Its Goal and scope are the human's call, so an agent may propose one but never opens it: an agent that finds work too big for one task runs `ergon new epic "Title"` (it starts `proposed`), fills in Goal / Out of scope / Constraints, files the tasks it can see under it with `--epic`, and tells the human. Nothing in the epic runs until a human approves its brief with `ergon approve E-NNN`.

## Epics → tasks

1. A human or an agent writes the epic: `ergon new epic "Title"` (it starts `proposed`), then fills in Goal / Out of scope / Constraints. A human approves the brief with `ergon approve E-00N`, which opens it. `ergon reject E-00N --reason R` drops an unwanted brief instead. `ergon review` lists proposed epics under EPICS AWAITING APPROVAL.
2. Once the brief is approved, `ergon dispatch` breaks the epic down by itself if it has no tasks yet (see Dispatch, **Breakdown**), and `ergon breakdown E-00N [--budget USD]` does it on demand. Either way, one read-only opus agent (`task-breakdown`) replies with TASK blocks, and each block that passes `check`'s rules is filed as a `proposed` task with `source: breakdown E-00N`. An interactive agent asked to "break down E-00N" does the same by hand. It reads the epic and the source, creates tasks with `ergon new task … --epic E-00N` (a feature with 2 to 4 `--option`s, see the one rule), one change or one human action each, fills in What / Done when / `tier`/`tier_why`/`depends`/`touches` and **stops**. It doesn't start any of them.
3. The human runs `ergon review`, edits or rejects what's wrong, and runs `ergon approve E-00N` to approve the rest at once. On an epic that is still `proposed`, that first approves only the brief; running it again approves the tasks.
4. When every task is done or dropped, the epic closes and its branch merges into the trunk (see below).

Re-breaking an epic later (`ergon breakdown E-00N` again) only adds new `proposed` tasks. It never edits existing ones.

## One branch per epic

- **Start.** `ergon start E-00N` cuts `epic/<epic folder name>` from the trunk (`trunk` in `.ergon.toml`, default `main`) and checks it out in its own worktree, `<worktrees>/E-00N` (default `.claude/worktrees`). Your checkout stays on whatever branch it's on. Moving an epic's first task to `doing` with `set` does the same, then refuses and tells you to `cd` into that worktree and run it again. If the branch is already checked out somewhere, `start` just tells you where.
- **Work.** Work an epic in the checkout that has its branch. Task files are shared by every worktree (they live in the main checkout). Every commit for the epic's tasks goes on that branch, including nested-repo gitlink bumps, and cites the task ID. Once the branch exists, `set` refuses status changes on the epic's tasks from any other branch. Marking a non-`human` task `done` warns if no commit on the branch cites it.
- **Several epics at once.** One worktree per epic, one session (or dispatch run) per worktree. `new`, `set`, `start`, `finish` and each dispatch step take a lock on `<state>/items/.lock`. Epics that touch the same files will conflict when the second one merges; `dispatch --dry-run` lists tasks whose `touches:` overlap.
- **Finish.** When `set` marks the epic's last open task `done` or `dropped`, it merges the epic branch into the trunk with `--no-ff` without switching any checkout. The merge message is `Merge E-00N: <title>`, followed by the epic's Goal and each task with the commits that cite it. Then it removes the epic's worktree (or detaches it if you're inside it or it holds untracked files), deletes the branch, and sets the epic `done`. It merges locally and **never pushes**.
- **If the merge can't run** (uncommitted changes in the epic's checkout, a conflict, or local changes where the trunk is checked out), nothing changes and `set` says why. Fix it (for a conflict, merge the trunk into the epic branch), then run `ergon finish E-00N`. `set E-00N status=done` is refused, so an epic can't close with its branch unmerged.
- **A conflict with the trunk, resolved by an agent.** `ergon finish E-00N --resolve [--budget USD] [--timeout MIN]` hands the conflict to a resolver: one `claude -p --agent task-opus` in the epic's worktree (`start`'s, made if there is none) on `epic/<name>`, run outside the state lock. Its prompt names the trunk, the conflicted files, the trunk's commits since the fork (`git log --oneline <fork>..<trunk>`), the epic's Goal and Constraints and each done task's title, so it knows what each side meant. **Its contract** is a conflict round's (see Dispatch, **Conflict rounds**): `git merge <trunk>`, resolve only the conflicted hunks, commit the merge citing the epic ID, nothing else; it ends `RESULT: done` or `RESULT: blocked — <why>` (no one answers questions there). **The checks:** the worktree is clean, the tip is a merge commit with the trunk's tip as a parent whose message cites `E-00N`, no `<<<<<<< ` / `>>>>>>> ` line is left in a file the branch changes, the branch now merges cleanly, the weakening check finds nothing the merge itself adds beyond both sides (a gate file that differs from both parents, so a conflicted gate file is yours to merge, or an added line in neither parent matching a `[gates] suppress` marker; a `verify` row with `layer: "weaken"` records a veto), and then the trunk's gates (`[gates]` static and runtime, or `verify`) run in that worktree. Any miss (or a block, a question, a red gate) merges nothing: the epic branch is put back where it was (the message gives the attempt's commit, to bring it back by hand), the epic stays open, and `finish` prints why and exits non-zero. On a pass, the usual finish runs under the lock, so the trunk's history has the resolution commit and then `Merge E-00N: <title>`. With no conflict it just finishes. Without `--resolve`, `finish` is unchanged; its conflict message suggests `--resolve`.
- **In dispatch**, when a task's landing completes its epic and the epic's branch conflicts with the trunk, the same resolver runs once (outside the lock, after the task's own landing) when `conflict_rounds` is above 0, its call capped at `--budget` and counted in the task's cost toward `--budget-total` (it doesn't start if it would cross the cap, as for a conflict round). Then the epic finishes under the lock. With `conflict_rounds = 0`, or when it fails, dispatch prints `E-00N is complete but not merged: <why>`, with the `--resolve` hint, and the epic stays open. A resolver's log is `<state>/runs/resolve/E-00N-<time>.json`. History: a `conflict` row (`task` null, the epic set), a `worker_end` row for the resolver (`tier: opus`, `after: "conflict"`), a `verify` row per gate, then `epic_finished` as usual.
- **What the epic resolver is shown** of the trunk side: the same list of tasks that landed on the trunk since the epic's fork (title, What, Done when, quoted, capped), beside the epic's own brief and tasks; it must keep each listed Done when true.
- Nested repos (gitlinks) aren't branched. Their commits land on their own default branch; the epic branch only carries the bumps.
- **Dispatch needs only the branch, not the worktree.** Dispatch cuts the epic's branch as a ref and never checks it out, so it works with no epic worktree. The epic worktree (`<worktrees>/E-00N`) is for humans and exists only after `ergon start E-00N` (or an epic resolver run). Once a worktree holds the epic branch, task landings merge inside it (`merge_into`, `ergon/gitops.py:149`), so uncommitted edits left there can block a task from landing: commit or discard them.

## Dispatch: headless workers, one worktree each

`ergon dispatch` runs `ready`, unblocked tasks without anyone watching. Run it from the main checkout.

```
ergon dispatch --dry-run               # what would run
ergon dispatch                         # up to 6 tasks, 3 at a time
ergon dispatch --epic E-012 --tier sonnet --jobs 2 --budget 5 --budget-total 20 --budget-pct 80   # $5/worker, stop launching at 80% of $20
ergon dispatch --ids T-202,T-188
ergon dispatch --watch --budget-total 20 --interval 30   # keep running; pick up tasks you approve meanwhile
```

- **Approved meanwhile:** any run, `--watch` or not, rescans every `--interval` seconds while a worker is running. A task you approve mid-run that shares no `touches:` path with a running task launches at once, beside the others (its launch line says `(approved during this run)`); one that overlaps is held and launches when its blocker lands (or at once beside it, within `overlap`; see **Overlap**). It counts toward `--max` and `--budget-total`. Without `--watch` the run still ends when nothing is running.
- **Drain (no `--max`, no `--watch`).** Plain `ergon dispatch` works the queue until it is empty: every eligible task, human-approved and auto-approved follow-ups alike (including those filed during the run), with no `--max` count and `follow_ups` ignored. It needs no `--budget-total`; with none it prints at the start that spend is uncapped, and the summary prints the total spent. `--budget-total`, `follow_up_depth`, `overlap`/holds, the usage-limit pause and Ctrl-C still apply. The run ends by itself when nothing is running and a scan finds no launchable task; a task held behind a running one, or `limited` before its reset, keeps it alive (it waits for the reset), while `blocked`, `asking`, `review` and `proposed` tasks don't. Give `--max N` for the old bounded run (then `follow_ups` bounds follow-ups). In every mode, when a cap (`--max`, `follow_ups`) keeps a ready task from launching, dispatch prints once `capped  <cap> keeps T-… from launching`, and `--watch` says so when only capped tasks are left. `--dry-run` prints `mode       drain` for it.
- **`--watch`** keeps the dispatcher alive, rescanning for newly `ready` tasks every `--interval` seconds (default 30) until the cap is reached or Ctrl-C. It requires `--budget-total`, and `--max` doesn't limit it unless given. The state lock is held only during a scan, so `approve` works between scans. Ctrl-C once: no new launches, running workers finish. Ctrl-C twice: workers are killed and their tasks marked `blocked`.
- **Breakdown.** Each scan (every scan with `--watch`) also breaks down every open epic whose brief is approved, that has no tasks at all and has never been broken down (no `breakdown` history row). Not with `--ids` or `--tier`; with `--epic`, only that one. It takes a `--jobs` slot but isn't a launch under `--max`. Its cost counts toward `--budget-total`, and `--budget` caps the call. `--dry-run` lists it as `would run  breakdown E-NNN` with its estimate. It is one `claude -p --agent task-breakdown` (opus; a project's `.claude/agents/task-breakdown.md` wins) in the main checkout. Its tools are Read, Grep and Glob, plus Bash for read-only commands only: the permission mode is `dontAsk` and only `git log/show/diff/grep/ls-files/blame/status`, `ergon show/next/check`, `ls`, `cat`, `head`, `tail`, `wc` and `grep` are allowed. The guard hook runs in read-only mode (`ergon hook guard --read-only`) on every tool call, so a write the allowlist lets through by mistake is still refused: it refuses every tool but Read, Grep and Glob, and any Bash that may write a file or change git state. Only read-only programs pass (git `log`/`show`/`diff`/`grep`/`ls-files`/`blame`/`status` and the like, ergon's read commands such as `show`, `next`, `check`, plus `ls`, `cat`, `grep`, `head`, `tail`, `wc`), with no redirect to a file, no heredoc and no variable assignment, and it fails closed (a crash refuses). Workers' guard is never read-only. If the checkout's `git status` (outside the state folder) changed during the run, nothing is filed. Its prompt holds the brief, the worker rules, the policies, the `[[protect]]` rules and the tasks already in the tracker. It ends with `TASK:` … `END TASK` blocks (title, `tier`, `tier_why`, `category` (empty reads as feature), `touches`, `depends` by the number of an earlier block or an existing T-NNN, `## What`, `## Done when`, `## Options`, optionally `## Notes`; the options are a `Crux:` line and 2 to 4 lens options, `- <lens>: <approach>` with `Optimizes for:`, `Gives up:` and `Regret if:` lines, in the order minimal, durable, operator, risk, defer, peers with none marked, within the epic's Goal and Constraints) and `RESULT: done`. A block with an unknown field, a tier below a `[[protect]]` minimum, an unknown category, a feature block with no options, an `## Options` section with recommendation wording, a repeated lens, a missing field, a too-short option, no Crux or an old numbered list (a bugfix, refactor or chore may have none), an empty What or Done when, no END TASK, or a dependency on a refused block is refused with a warning, never repaired. A `RESULT: blocked — <why>` files nothing, and dispatch doesn't run that epic's breakdown again: `ergon breakdown E-NNN` does. In shared mode dispatch claims the breakdown first by pushing a `breakdown:` field on the epic (see shared mode above); a clone that finds another's live claim prints `claimed  breakdown E-NNN  another dispatcher holds it (…)` and leaves it, and the claim comes off when the run ends, so a blocked run on one clone doesn't stop another clone from trying once. Logs go in `<state>/runs/breakdown/`. `ergon serve`'s epic page lists the epic's breakdown runs (verdict, cost, time, log link), and `ergon stats` prints their runs and cost on a line of their own (`--epic E` limits it to that epic).
- **Per task:** a worktree at `<worktrees>/<ID>` on branch `task/<ID>`, cut from the epic branch (created as a ref if needed, never checked out) or from the trunk. A headless `claude -p --agent task-<tier>` works the task there: model = tier, permission mode `auto` by default. The worker definitions are the plugin's `agents/task-<tier>.md`; a project overrides one with its own `.claude/agents/task-<tier>.md`. The project's `worker_rules` file is inlined into every worker's prompt. So is the **policies file** (`policies` in `.ergon.toml`, default `<state>/policies.md`: in local mode that file is yours alone, not on the trunk; in shared mode `<state>/` shares only `items/` and `epics/`, so set `policies` to a trunk path such as `.ergon/policies.md` and commit it through code review, which `ergon sync --init`/`--join` hint at), inlined after the rules into worker and reviewer prompts; the reviewer is told not to raise a finding a policy settles. It is sreview's format: `## Stances`, then `### P-n <title>` with Why / Applies to / Examples / Decided `<name> <date>`. **Only a human writes it**: the interactive review (`ergon review` with its interactive flag) offers `p` on a task held in `review` or blocked on a review veto (prompts for title, why, applies-to; offers `$EDITOR` to refine), and the guard refuses agent writes to the file. An agent proposes one with a `POLICY: <title> — <why>` line before its RESULT line; dispatch records it as a note on the task. **Enforced policies retire from prompts**: when a harden task lands, dispatch (never a worker) appends `- **Enforced by:** <ID>` to every policy whose `Examples:` cite a task one of its incidents came from; worker and reviewer prompts then show that policy as one line (`P-n is enforced by <ID>; the gate will catch it`) instead of its body. `ergon check` warns, without failing, on a policy over 14 days old with no `Enforced by:` and no open harden task covering it: a nudge to run `learn`.
- **Companion repos.** A `[[companion]]` in `.ergon.toml` is a separate repo checked out inside this one (a public product repo next to a private install, say). A task whose `touches:` names it gets its own git worktree of that checkout, at `<task worktree>/<companion path>`, on a `task/<ID>` branch cut from the companion's local trunk. The worker commits there, never in the shared checkout; the `--worker` guard refuses edits, shell writes and mutating `git` aimed at the shared checkout. With `forbid_tracker_ids = true`, companion commits must not cite task IDs; the worker's own commit cites the task and names the companion commit. A task that doesn't name the companion gets no checkout of it. Tasks naming a companion with no checkout are skipped.
- **Obsidian write-back.** With `[obsidian]` `write_back = true`, dispatch runs the ticking step of `ergon obsidian` (not intake) once after its last worker ends and prints `Obsidian: ticked T-NNN in <note>` per change, `Obsidian: couldn't find T-NNN's line in <note>` for a missing line. `--watch` runs it after each task that lands; `--dry-run` lists what it would tick. A failure only prints `warning: Obsidian write-back failed: …` and changes no task status or exit code. In an agent shell it writes nothing. Without `write_back` it prints nothing about the vault.
- **Status is the dispatcher's.** It sets `doing` at launch. Workers never run `ergon set` (it refuses on a `task/` branch); they end with `RESULT: done`, `RESULT: blocked — <why>` or `RESULT: asking` (below). Work they find but don't do goes on `FOUND: <title> — <why>` lines before the RESULT line, each followed by at least one `DONE WHEN: …` line (required; repeatable, and a bare `DONE WHEN:` followed by `- item` lines gives one item per bullet) and optionally `TOUCHES: a, b`, `TIER: haiku|sonnet|opus|human — <why>` and `CATEGORY: feature|bugfix|refactor|chore` lines (feature: new behaviour a user would notice; bugfix: existing behaviour is wrong, security holes included; refactor: same behaviour, better code; chore: docs, help text, tests, config, tooling; a missing or unknown CATEGORY leaves `category:` empty, which reads as feature); after the run (done or blocked) each becomes a task (`touches`, Done when and tier from those lines, else the finder's tier with a `tier_why` saying to size it; same epic, `source:` the finding task), listed in the run summary. A feature needs a `CRUX: <what the choice turns on>` line and 2 to 4 peer `OPTION: <lens>: <approach> — optimizes for … — gives up … — regret if …` lines, one per lens (minimal, durable, operator, risk, defer), one of them `defer`, none marked as better than the rest: it is filed with them as its lens-format `## Options` section (in lens order), so it can't be approved until a human chooses. A feature with a malformed set (no `defer`, recommendation wording, a repeated lens, a missing field, a too-short option, no crux) is still filed `proposed` with no `## Options`, and a Notes line `options from <finder> not filed: <each problem>`; one with no options gets `no options given by <finder>: …`. A bugfix, refactor or chore ignores `CRUX:` and `OPTION:` lines. An `OPTIONS:` line belongs to the `QUESTION:` line directly before it; after a FOUND line it is ignored. The reviewer sees each finding's crux and options. A feature, and anything that misses one of the six conditions in "The one rule" (category bugfix, refactor or chore; tier not human; declared touches, none protected; within `follow_up_depth`; local mode; a non-empty Done when), is filed `proposed` and you approve it like any other (one filed with no Done when gets a Notes line: `ergon fill <ID>` writes one); so is everything a run files when it didn't finish `done` or held for `accept`. The rest is filed `ready` with an `approved: auto …` stamp, approved by inheritance from the finding task, and the same dispatch run picks it up at its next scan: an original task is complete when it and every auto-approved follow-up under it are closed. Follow-ups don't count toward `--max`; they do count toward `--budget-total` and its cap, and `follow_ups` in `.ergon.toml` (default 10) bounds how many launch in one run, the rest staying `ready` for the next (`--dry-run` says so, and that the `--budget-total` estimate leaves them out). The run summary splits what was filed into `auto-approved, worked this run` (with outcome), `auto-approved, left ready` and `proposed, need your approval`. A done task with open follow-ups (anyone whose `source:` chain leads to it, not done or dropped) reads `done, N follow-ups open` on the board, on its `/t/T-NNN` page (which lists them with category and status), in `ergon show` and in `ergon report`. A reviewer, where `review` names the tier, is shown the worker's FOUND lines with their categories and told to fail the branch if a non-feature follow-up is really new behaviour or hides security-sensitive work behind `bugfix`.
- **`--until-done N`** (default 0: a worker that stops short blocks its task, as before). This covers the first worker and the workers of verify, review and conflict fix rounds alike (a stopped fix or conflict worker is retried on the same branch, and its retry prompt carries what the round was fixing). A worker run that times out (at `--timeout`), errors, prints output that isn't JSON or ends without a `RESULT:` line runs again on the same branch, inside the same dispatch, up to N more rounds. Its session is resumed by the `resume_choice` rules of fix rounds, or a fresh worker starts with the earlier attempt's commits; the prompt says how it stopped and to carry on from there, and a worker that needs a decision ends with `QUESTION:` lines and `RESULT: asking`. After a round says done, the done checks, verify, review and conflict rounds run as usual, and their rounds count apart from until-done rounds. Not retried: a worker's own `RESULT: blocked` (it files a human task; `--escalate` covers it), `RESULT: asking`, a second Ctrl-C, the `--budget-total` cap (no round starts if it would cross it, as for fix rounds) and a stop by the 5-hour limit. Rounds out, the task blocks with each stop's reason in Notes, last first. `--dry-run` says `up to N until-done rounds` and counts N more worker calls per task in its estimate. A round's log is `<ID>-<time>-fix<N>.json`.
- **The usage limit.** When the plan's limit (5-hour, or weekly) runs out mid-run, a worker or reviewer that hits it ends with the limit's message (`claude -p` reports `is_error`, a 429 and text like `You've hit your 5-hour limit · resets 10pm (Europe/Lisbon)`, or on older versions `Claude AI usage limit reached|<epoch>`; `limits.stop()` holds the patterns). Dispatch reads the reset from the message; failing that it asks the window probe, and failing that it tries again 30 minutes later. It parks the task `blocked` with `limited: <reset, UTC ISO> <step>` in its frontmatter, where `<step>` is where it stopped: `worker` (the first worker, an answered, escalated or until-done one), `fix N`, `verify N` (a verify, weaken, prove, harden or evidence round), `conflict N` or `review`. It writes a `dispatch: limited:` note and a `limited` history row. No human task is filed, `--escalate` doesn't retry it, and the stop uses up no fix, verify, conflict or until-done round. The worktree, branch and session stay, and the call's cost still counts. The run then launches nothing more before the reset: workers already running finish, or park the same way. A plain run ends with `paused by the 5-hour limit until HH:MM: T-…`; `--watch` waits for the reset and goes on. Any dispatch scan at or after the reset moves a `limited` task back to `doing`, clears the mark and restarts that step. The recorded reset may be stale — the `claude` login was switched to an account with a fresh window, or the limit lifted early — so while anything waits on it each scan re-checks the limit with one window probe (`limits.active()`): a result that isn't a limit stop resumes the parked work at once, a limit stop waits out the fresher reset it names, and an inconclusive probe (`limit_probe = false`, no window, a failed call) keeps the plain wait. A worker or round resumes its session by the `resume_choice` rules (after a long wait usually a fresh worker on the branch, told what the round was fixing). A `review` stop runs the gate again, so the reviewer reruns but the worker doesn't. Its FOUND and EVIDENCE lines carry over. History records the `dispatched` row (and a `resumed` one) with `after: "limit"`. Before the reset, `--dry-run`, the run's skipped list and the board show `limited until HH:MM`. Only dispatch writes the mark: the guard refuses agent edits to it, `ergon set` refuses to write it or to move a `limited` task, `ergon check` fails a mark on a task that isn't `blocked`, and a human's close clears it. `approved:` is never touched.
- **Questions.** A worker that needs a decision, rather than giving up with `RESULT: blocked`, ends with one `QUESTION: <text>` line per question, each optionally followed by `OPTIONS: a | b | c`, then `RESULT: asking`. It can do this on its first run or in any fix round. Dispatch keeps the worktree and branch and frees the job slot. It sets the task `blocked` with `asking: <session>` in its frontmatter, writes a `dispatch: asking:` note with one `question:` bullet per question under it, and records a `question` event. No human task is filed, and `--escalate` doesn't retry it. `RESULT: asking` with no `QUESTION:` line blocks the task as usual. Options are `<lens>: <approach> — gives up <cost>` entries split on ` | `, shown in lens order (minimal, durable, operator, risk, defer) with none recommended; an entry with no known lens is kept and listed after the lensed ones. `ergon answer` takes a lens name (or your own words); an old `[options: a | b]` note still reads and answers by number. `ergon review`, `/review` and `/t/T-NNN` list the questions the same way.
  - **Answer.** `ergon answer T-NNN "<text>"`, or `ergon answer T-NNN` alone, which shows each question's options and takes a number or your own words. It is human only (see the rule above). It prints the questions and the re-plan warning, asks you to confirm, writes `answer by <name>: <text>` to Notes, swaps `asking:` for `answered: <session>`, sets the task `ready` and records an `answered` event. Nothing else in the file changes. While a task is `asking`, `ergon set` refuses to move it and refuses to write either mark. `ergon close` gives the question up and clears the mark. `ergon check` fails a task whose `asking:` isn't `blocked` or whose `answered:` isn't `ready`.
  - **Resume.** The next dispatch clears `answered:` at launch and resumes the worker's own session with the questions and the answer, by the same `resume_choice` rules as fix rounds (`review_resume_secs`, `review_resume_tokens`). Once the prompt cache has likely expired, which is the usual case after a human's wait, it starts a fresh worker on the same branch instead. The questions and answer are in its prompt, along with the task file and its Notes. Either way the worker is told the answer can't change tier, `touches:`, `accept:` or approval, and to end `RESULT: blocked — re-plan: <why>` if it would. From there the run goes on as usual: done checks, verify, review, landing. It may ask again. `--dry-run` marks such a task `resumes with your answer`, and the run summary lists every task waiting on you under AWAITING YOUR ANSWER.
- **Verify.** An optional `verify = "<shell command>"` in `.ergon.toml` (a task's `verify:` frontmatter overrides it) runs in the task worktree after the done checks and before any merge, with a 15-minute timeout. A non-zero exit or timeout blocks the task: the last lines of output go in Notes, the full output in `<state>/runs/<ID>-<time>-verify.log`, and the worktree and branch stay. No key, no check. Keep `#` out of a task's `verify:` value (frontmatter treats ` #` as a comment).
  - **Layers.** `[gates]` in `.ergon.toml` takes `static` (lint, types, import boundaries) and `runtime` (tests). They run in that order and stop at the first red; `verify` is an alias for `runtime`, and a task's `verify:` overrides `runtime` only. Each red feeds the verify rounds below (counted per task, not per layer) with its layer named in the prompt, and the `verify` history row carries `layer`. The worker prompt lists the gate commands, and `--dry-run` prints them.
  - **Evidence.** A worker may end with `EVIDENCE: <path in worktree> — <what it shows>` lines (test output, screenshots, recordings), parsed like `FOUND:`. Before the gates' review, dispatch copies each file (regular files inside the worktree only, no symlinks, 5 MB cap, 20 files) to `<state>/runs/<ID>-evidence/` and records an `evidence` history row (`files`, `refused`). The reviewer prompt lists the files with their captions and tells the reviewer to read them; `ergon serve`'s `/t/T-NNN` shows them (images inline, other files linked through `/runs/`, all escaped). `evidence: yes` on a task, or an `[[evidence]]` rule in `.ergon.toml` (`tiers`/`touches`, matched like `[[accept]]`), makes evidence required: a done with none goes to a fix round that uses up `verify_rounds`.
  - **Weakening check.** The cheapest way past a gate is to edit the gate, so before `static` a deterministic check reads the branch's diff against its base (`git diff <base>...task/<ID>`, and each companion's against its trunk). Three things count as weakening: changing a **gate file** (`[gates] protect = ["ruff.toml", ".eslintrc*", "tests/arch/**"]`, fnmatch patterns where a directory covers what's under it and a pattern with no `/` also matches that name in any directory; `.ergon.toml` is always one; list every file your gate commands read, such as a lint script or the `pyproject.toml` that holds rules), and **changing or deleting a kept reproduction** (a file under `<[gates] repros>/` that exists on the base, vetoed unless `touches:` names that file; a harden task adding its own new reproduction is unaffected, T-161), and **adding a line that matches a suppression regex** (`[gates] suppress = ['# noqa', 'eslint-disable', '@pytest\.mark\.skip']`, TOML literal strings; none by default) in any file. A gate-file change is allowed only where the task's `touches:` names that file: the path itself (a companion file as `<name>/<path>`), or the protect pattern it falls under, written the same way. A directory or a wider glob doesn't count. An approved task naming the file is a harden task. An added marker is vetoed in every file, named or not, unless the task is a harden task (`harden:` set) whose `touches:` names that file (T-118): most of what an ordinary task edits is in its `touches:`, so naming alone would let it silence a check in nearly any file it changes. `harden:` is human-only, like `touches:` (`set` and the guard refuse it, and it is in the brief digest), so a worker can't opt itself in. An ordinary task with a real need for a marker (a re-export's `# noqa: F401`) gets it from `suppress_ok: [<file>, …]` (T-160): a marker added to a file it names passes, harden task or not, and `touches:` needn't name the file. It names files one at a time, as `touches:` names a gate file (a companion file as `<name>/<path>`): a directory or a glob exempts nothing, and `ergon check` refuses a glob. It exempts the marker only: a gate file it names is still a gate file `touches:` must name, and a kept reproduction is still checked. It is human-only like `harden:` (`set` and the guard refuse it, and it is in the brief digest), so a worker that needs one ends with a `FOUND:` line and a human writes it. One exemption needs no `touches:` entry: a harden task's own reproduction, `<[gates] repros>/<incident id>.patch` for each id in its `harden:` (as at launch, and approved: see below), in the main repo, passes the gate-file and marker checks (T-121). It is the incident's bad diff, so it may hold the very marker the incident was about, or sit under a protect pattern, and no one can name it before the proof asks for it. Only those files: another file under `repros`, or the same file from a task without that id in `harden:`, is checked as usual, and one the base already keeps is still a kept reproduction that `touches:` must name. The check reads the task as it was at launch, like `accept`, so a worker that edits its own `touches:` to cover the change gets nowhere in that run. Nor in a later one: only the `touches:` a human approved count. Each `approved` history row records the task's `touches:` as approved, and a launch records them on its `dispatched` row when no row since the last approval has (a task stamped by hand, or approved before rows held them). An entry added to the file after that (the guard refuses the edit; this holds when it was bypassed, and in local mode, where no brief digest notices) exempts nothing: its finding says the entry came after the approval. A human who widened `touches:` by hand runs `ergon approve <ID>` again, which in local mode re-approves a `ready` or `blocked` task whose `touches:` gained an entry (shared mode's digest un-approves it anyway). The record only narrows: an entry counts only if the task file names it too. `harden:` is recorded beside `touches:` on the same rows and read back the same way (T-162): only an id a human approved makes the task a harden task for the marker check and exempts its own reproduction, so an id added to the file after the approval exempts nothing (its finding says so) until `ergon approve <ID>` runs again, which in local mode re-approves a `ready` or `blocked` task whose `harden:` gained an id too. `suppress_ok:` is recorded and read back the same way: a file added to it after the approval exempts nothing (its finding says so) until `ergon approve <ID>` runs again. The check is on what lands; guarding gate files against edits at the tool call is the guard hook's side (T-069). A veto records a failed `verify` row with layer `weaken` and its `findings`, saves an incident, and goes into a verify fix round that tells the worker to revert the change to each file and, if the rule itself is wrong, to say so on a `FOUND:` line. These rounds use up `verify_rounds` like any red gate. Unfixed, the task blocks with the findings in Notes. The worker prompt lists the gate files and markers up front.
  - **Incidents.** Whenever a layer above static catches something (a red runtime gate, a review `fail`, a weakening veto, a human `reject` of a task in `review`), dispatch or reject saves `<state>/runs/incidents/<ID>-<time>.patch` (`git diff <base>...<tip>`; a companion's diff goes in `<ID>-<time>-<name>.patch`) and `<ID>-<time>.json` (`task`, `layer`, `reason`, `log`, `base`, `tip`, `tier`), and records an `incident` history row naming both. They stay when a fix round goes green: they are the mistake in a form a check can run against. Saving is a `git diff` only, so `reject` stays fast and offline.
  - **Harden tasks.** A task with `harden: [<incident id>, ...]` turns those incidents into a deterministic check (a lint rule, an import boundary, a type, an arch test), never a sentence in a doc or a prompt, and lands only once dispatch has proved the check catches them. Its `touches:` names the gate files it changes, and any file it adds a suppression marker to, so the weakening check lets them through. Its worker prompt lists the incidents (layer, reason, patch path) and the proof. After the gates pass on the branch, in a scratch worktree (`<worktrees>/<ID>-harden`, removed after), dispatch runs the `harden_layer:` gate (`static` by default, or `runtime`) on: each incident's patch applied to the branch (plainly, else a 3-way merge), which must go **red**; the same patch applied to the branch's merge-base, without the check, which must be **green**, or the red proves nothing about the check (the replay is broken, or an older gate already flags it); and the merge-base with only the branch's gate-file changes (`[gates] protect`) and no patch, which must be **green**, so the check flags the incident and not code already there (a branch that rewrites existing code to pass its own check fails this; fix that code in a task of its own). A patch that can't be replayed both ways is reported, never passed: the worker is asked for a minimal reproduction, a `git diff` against the branch that the check must flag, committed at `<[gates] repros>/<incident id>.patch` (default `tests/harden`). The proof replays it where the incident's patch can't be, and it lands with the task as the check's test. Since a harden task may change gate files, one that adds a check can quietly weaken an older one, so once its own proof holds, dispatch replays **every other reproduction kept on the merge-base** (`<[gates] repros>/*.patch`, the tests earlier harden tasks landed, the base's copy of each) on the branch with the same gate. Each must still go **red**. One that stays green while the gate is red with it on the base (and green on the base alone) is a miss: the proof fails, naming the reproduction and the gate. One that no longer applies is reported as `stale`, and one the gate doesn't catch on the base either (another layer's) or that the base can't judge (red alone) as `inconclusive`; neither fails the proof. This costs one gate run per kept reproduction on every harden task (one that stays green also runs on the base with it, and the base alone runs once), and `--dry-run` counts them. A miss (its own or a kept one's), an unreplayable patch or a red base goes into a fix round that shares `verify_rounds`; rounds out, the task blocks with the findings in Notes. A missing incident (they stay in the clone that saw them) with no reproduction, or no gate for the layer, blocks at once. Each proof records a `harden` history row, and its output goes to `<state>/runs/<ID>-<time>-harden.log`. Only the main repo's patch is replayed, not a companion's. `ergon check` refuses a `harden:` entry that isn't an incident id and a `harden_layer:` other than `static` or `runtime`.
  - **Red-on-base proof.** A green runtime gate proves little if the branch's tests would pass without its change. `[gates] tests = ["tests/**", "**/*_test.go"]` names the project's test files (fnmatch like `protect`, except that a pattern with no `/` matches a file or directory name at any depth, and a leading `**/` matches at the root too). When a branch adds or changes a file matching it, after the gates go green dispatch makes a scratch worktree (`<worktrees>/<ID>-prove`, always removed) at the branch's merge-base with its base, overlays only the branch's test files (added, changed and deleted, by path with `--no-renames`: a renamed test is the old path deleted and the new one added, and a shared fixture counts if it matches), and runs the runtime gate there. It must go **red**. Green (or a timeout, which proves nothing) goes to a fix round that shares `verify_rounds`: "your tests pass without your change; make one fail on the base". A worker that ends that round `RESULT: blocked — outside: <why>` (no behaviour to pin: docs, a refactor) waives the proof for the rest of that dispatch at no round's cost, and the task's Notes say why. A branch that changes no test file, or only deletes tests, skips it. So does a task with `prove: no` (read as at launch), a tier not in `[gates] prove_tiers` (default every worker tier; `[]` turns it off), a harden task (its own proof replays its incidents), and a project with no runtime gate. Each run records a `prove` history row and writes `<state>/runs/<ID>-<time>-prove.log`; a green-on-base run counts as a `prove` catch in the trust pyramid, and `stats` prints the proof's runs, time and the cost of the fix rounds it sent back. The worker prompt says the proof will run, and `--dry-run` names it.
  - **Learn.** `ergon learn [--since YYYY-MM-DD] [--model sonnet] [--budget USD] [--dry-run]` turns recurring incidents into proposed harden tasks. It sends one `claude -p` with no tools, from an empty folder (the same call `quiz` and `grade` make): every incident no task's `harden:` cites yet, newest first, at most 40 (`--since` drops older ones); the open `proposed` harden tasks; and the policies file and the worker rules, as prose a check could replace. A cite from a closed task counts too: a dropped harden task is a no, not a prompt to propose it again. Incident text is fenced as data. The reply is mistake classes. Each class has its incidents, the lowest layer that could catch it (`constraint`, `static`, `runtime`, `review`, `human`), a sketch of the check, a `crux` (what the choice turns on) and 2 to 4 peer alternative checks at that layer as `options` (objects with `lens`, `approach`, `optimizes_for`, `gives_up`, `regret_if`; one per lens, none recommended; a set that fails the lens checks is left out of the task with a Notes line), a title, a tier and touches. A new task writes a valid set (trimmed, capped at 4) as its lens-format `## Options` in lens order, so approving it waits on `ergon choose`; a class with no options, or a set with recommendation wording, a repeated lens or a missing field, is still filed with no `## Options` and a Notes line saying no options were offered and naming the problems. A class that joins an open task never changes that task's `## Options` (a `Chosen:` line may name one): its lens entries go in the Notes only. Each class becomes one `proposed` task with no epic, filed the way FOUND lines are: `source: learn`, `harden:` its incidents, tier `sonnet` unless the class says otherwise, and `harden_layer:` the gate the proof replays on (`constraint` counts as `static` when a static gate is set, else `runtime`). A `review` or `human` class has no gate to replay on, and its fix (a policy, an `[[accept]]` rule) is a human's to write, so it is filed human-tier with no `harden_layer:`. A class naming an offered proposed harden task adds its incidents to that task's `harden:` and a line to its Notes instead of filing a new task. Joining changes that task's brief digest (`harden:` is in it), so an approval in progress goes stale; only proposed tasks are joined, so an approved one never changes this way. Filing a new task changes no signed approval. A class of one incident is filed only at `review` or `human`; any other waits, uncited, for a second of its kind. The reply is trusted only for incidents that were asked about, each claimed once. A class with an unknown layer, no usable incident or a title that wouldn't survive frontmatter is refused with a warning. A `[[protect]]` minimum raises a class's tier. A reply that isn't a JSON object with a `classes` list files nothing, warns and exits non-zero. Each run that asks writes `<state>/runs/learn/learn-<time>.json` (incidents asked, the reply, what it filed, the cost) and a `learned` history row. It asks only when an uncited incident is waiting that no earlier successful run asked about, so a rerun costs nothing until something new is caught. It only proposes, so agents may run it. With `learn = true` in `.ergon.toml`, dispatch runs it when the run ends (not after a Ctrl-C), and with `--watch` from each scan that finds a new incident (in a `--jobs` slot, one at a time). Its cost counts toward `--budget-total`, the call is capped at what's left of that (and at `--budget`), a failure only warns, and `--dry-run` lists it as `would run  learn`.
  - **Verify rounds.** A red verify goes back to the worker, inside the same dispatch, up to `verify_rounds` times (`.ergon.toml`, default 2; 0 blocks on the first red, as before). The worker's session is resumed (or a fresh worker started, by the same rules as review fix rounds) with the last ~200 lines of output and the full log path, then the done checks and verify run again. Rounds out: the task blocks with the last output in Notes.
  - **`outside:`.** A worker that finds the failure isn't caused by its branch (a flaky test, a broken trunk, a missing tool) changes nothing and ends `RESULT: blocked — outside: <why>`. That attempt doesn't use up a round: verify reruns once as it is. Green lands the task (Notes record the reason). A second red blocks it, and dispatch runs the failing gate once on a clean worktree of the base. Red there too: it files a `proposed` **sonnet** task "Make <layer> gate green on <base>" (the log and the worker's reason in What, `source:` the blocked task) and the blocked task depends on it; a second blocked task on the same base and layer joins the open fix task instead of filing another. Green there (flaky or environmental): it files a `human` task with the worker's reason and both logs, the way any `RESULT: blocked` does. This is sclaude's regression rule.
- **Review.** Opt-in: `review = ["haiku", "sonnet"]` in `.ergon.toml` lists the worker tiers whose branches a reviewer has to pass before they land. No key means no review. After `--escalate`, a task is reviewed if either its own tier or the one that finished is listed, since the lower tier's commits are still on the branch. The reviewer is one tier above the tier that finished, capped at opus: haiku→sonnet, sonnet→opus, opus→opus. It runs after verify and before any merge: `claude -p --agent task-review` in the task worktree, read-only (the plugin's `agents/task-review.md`; a project's `.claude/agents/task-review.md` overrides it, and dispatch always sets the model). Its prompt holds the task file, the worker rules, and `git diff <base>...task/<ID>` plus each companion's diff (only the `--stat` past 100k characters).
  - Only a last line of `REVIEW: pass` lets the task land. Anything malformed blocks it at once: no such last line, output that isn't JSON, an error, a timeout or kill, or a reviewer that moved the branch or left tracked changes. That leaves no findings to fix, so no fix round runs.
  - **Fix rounds.** A `REVIEW: fail — <why>` goes back to the worker, inside the same dispatch, up to `review_rounds` times (`.ergon.toml`, default 2). Each fix round hands the reviewer's reason and review log to a worker on the same branch, waits for its `RESULT:` line, then runs the done checks, verify and the review again (fix round N is review round N+1). A worker that says done but committed nothing since the review blocks the task, and so does a `RESULT: blocked` (filing the human task as usual) or any failure in the checks or verify. A pass ends the loop: the task lands or waits for your accept as usual, and Notes record the vetoes it fixed. `review_rounds = 0` blocks on the first fail.
  - **Resume or fresh.** A fix round resumes the worker's own session (`claude -p --resume <session>`, same agent, permission mode and guard hook) only while its prompt cache is likely alive and its context is light: its transcript's last request is younger than `review_resume_secs` (default 3300, the hour's cache TTL less a margin) and held fewer than `review_resume_tokens` (default 80000). Resumed after that, the whole context would be sent again uncached, so a fresh worker costs less. Otherwise, and whenever the transcript can't be read, a fresh worker starts on the branch with the retry prompt (the veto and its log, plus the earlier attempt's commits). The history records which: `resumed`, or `dispatched` with `round` and `fresh_because`. From SClaude's `review_keep`.
  - **When the rounds run out** (or a Ctrl-C, or the cap stops them), the task blocks the way verify does: Notes hold the last fail first, with its review log (`<state>/runs/<ID>-<time>-review[N].json`), why no further round ran, then every earlier round's reason. The worktree and branch stay, no human task is filed, and `--escalate` doesn't retry it. To retry, move it back to `ready`. The new worker's prompt quotes the last veto and points at its review log, and the rounds start over.
  - Each review and each fix round's worker counts toward `--budget` (per call), `--budget-total`, the run summary (`$X (reviews $Y of it)`) and the spend in `stats` and `report`, under the task's tier. Neither is counted as a run (a fix round's log is `<ID>-<time>-fix<N>.json`). With `--budget-total`, no fix round starts once what's spent (finished tasks plus every running task's calls so far) plus the cost of the round just finished would cross the cap. `--dry-run` marks a reviewed task `reviewed by <tier> (up to N fix rounds)`, and its `--budget-total` estimate counts each task at `--budget` times every call it may make: its worker, for a reviewed tier the review and two calls (a fix and a review) per fix round, one fix per verify fix round (`verify_rounds`), with or without a verify (a weakening veto or failed harden proof takes one too), with `--escalate` a second worker a tier up (counting the review if that tier is reviewed), and per conflict round (`conflict_rounds`) a worker plus the verify fix rounds and the review (with its fix rounds) that rerun after it. It sums the `--max` costliest planned tasks, so it is an upper bound whichever launch.
  - The reviewer is a second opinion, not a security boundary: it reads text the worker wrote, so a worker can try to talk it into a pass. Verify is the mechanical check.
  - The done checks, verify and review touch only the task's own worktree and branch, so they run outside the state lock. A slow one doesn't hold up other tasks landing.
- **Accept.** Opt-in: a task with `accept: yes`, or one matching an `[[accept]]` rule in `.ergon.toml` (`tiers = ["opus"]` and/or `touches = ["server/**"]`, fnmatch like `[[protect]]`; a rule with both needs both), doesn't land when its gate passes. Dispatch sets it `review` instead, notes how to accept or reject it, keeps the worktrees and branches, and lists it at the end of the run. `--dry-run` marks it `held for your accept`. Dispatch decides from the task as it was at launch, so a worker that edits its own task file can't skip the hold. After `--escalate`, the tier that finished counts too. `ergon accept` lands it later as dispatch would have (refusing while a worktree has uncommitted changes), always with a merge commit, `Merge T-NNN: <title>` plus `Accepted by <name> <date>`, so history keeps who accepted it. If the branch conflicts with its base (which moved while the task waited), nothing merges: the task goes back to `ready` with a Note, keeping its branch and worktree, and the next dispatch runs a conflict round on that branch, then verify and review, and holds it at `review` again for a fresh accept (the earlier one isn't carried over). If the base moved but merges cleanly, accept prints `merging T-NNN …` and does what a dispatch merge pass does (see **Merge passes**): it merges the base into `task/<ID>` in the task's worktree and runs the done checks, the weakening check and the gates there, outside the lock; under the lock it lands only if no base moved since, else it makes another pass, up to `remerge_rounds`. On a red gate, or when the passes run out, nothing lands: the task goes back to `ready` with a Note (`… the next dispatch runs the gates on its merge again (a fix round if red), and it returns to review for your accept`), keeping the branch with accept's merge on it. The next dispatch starts no fresh attempt: it runs the gates on that branch, a verify fix round if they're red (its prompt carries the merge, as above), the usual merge pass if the base moved again, and holds the task at `review` again. Any other failed merge makes the task `blocked` with the reason. A rejected task's next worker is shown the human's reason and picks up the same branch. Nothing opts a task out of a matching rule, and `ergon check` fails a task in `review` whose `task/<ID>` branch is gone.
- **5-hour limit.** On a subscription, dispatch reads the plan's 5-hour window just before it launches and again after the last worker ends, with one tiny haiku call each (about $0.003). Claude Code reports the window only to the whole percent and once per session, and workers share it, so no task's share can be read directly. Instead the run records the before and after readings and its cost in a `window` history row. Points per dollar, pooled over the last 10 runs whose window didn't reset, turn each task's cost into its share: the run summary lists every task's `$` and `≈ N% of the 5-hour limit`, and `ergon stats` adds `5h%` columns. Anything else using the plan during the run (an interactive session) counts too, so the shares are an upper bound. On an API key there's no window and nothing is shown. `limit_probe = false` in `.ergon.toml` turns the probes off.
- **Approver signals.** `ergon stats` prints a `red-on-base proof` section once the proof has run (runs, red, green on the base, waived, its time, and the count, cost and time of the fix rounds it sent back), then a `trust pyramid` section (catches per layer per week from the history: failed `verify` rows by their `layer`, old rows with none counting as `runtime`, failed `prove` rows as `prove`, review fails as `review`, rejects from review as `human`, guard refusals (`guard` rows, written by `ergon hook guard`) as `guard`; answers counted apart; layers it doesn't know are shown as they come) with the share caught by `review` + `human`, the number hardening should drive down, and `/metrics` charts it as stacked bars. It also prints an `approver signals` section (from the event history, falling back to the task file's `approved:` stamp): for the tasks an approver approved, how many landed, escalated, blocked (not `outside:` blocks, Ctrl-C or budget stops), asked or came back from review, fix rounds per landed task and the tier mix, with a per-week trend (`(n<3)` marks thin weeks). By default it shows only your own record (`--approver NAME` for another, `--approvers` for all); these are signals, not verdicts.
- **Done** means the worker said so, left no uncommitted changes (in any tree), a commit on `task/<ID>` cites the ID, and verify and review (where set) passed, on the branch merged with its base if the base moved (see **Merge passes**), and no human acceptance is required (see Accept). Companion branches are checked first (no tracker ID if forbidden, clean merges everywhere), then merged into each companion's local trunk, then the task branch into its base. Then the worktrees and branches are deleted (companions first), the task goes `done`, and if it was the epic's last task the epic closes. Nothing is pushed.
  - **Merge passes.** The gates ran on `task/<ID>` as it was cut. If its base moved since (the base's tip isn't an ancestor of the branch, checked per repo: the task's own, and each companion's trunk) and the merge is clean (`git merge-tree`), landing would put a tree on the base that no gate has seen. So, after the gate passes and outside the state lock, dispatch merges the base in itself, in the task's worktree, with no worker: `git merge --no-edit -m "Merge <base> into task/<ID> (<ID>)"` (in a companion with `forbid_tracker_ids`, `Merge <trunk>`, no ID). Then it reruns the done checks, the weakening check and the gates (static, runtime) on the new tip. Review doesn't rerun unless a fix round follows, since the merge adds no code of the worker's. The landed task's Notes say `merged <base>, which had moved; the gates passed on the merge`. A branch whose bases haven't moved lands exactly as before: no merge commit, no extra gate run.
    - **A red gate on the merge** goes to a verify fix round, through the same fix loop and out of the same `verify_rounds` as the task's other verify rounds in that dispatch. Its prompt says the branch was green alone and went red merged with its base, names dispatch's merge commit, lists the base's commits since the fork (`git log --oneline <fork>..<base>`) and gives the gate output, as a verify round does; the worker fixes its side on top of the merge. `outside:` applies as in any verify round. Rounds out, the task blocks (`red since dispatch merged <base> into task/<ID>; it was green alone`), worktree and branch kept, and the base never holds the broken merge.
    - **Under the lock**, just before it lands: if a base moved again since the gates ran (another task landed meanwhile), the task goes back outside the lock for another pass, as conflict rounds do, up to `remerge_rounds` passes in all (`.ergon.toml`, default 3). Out of passes, it blocks: `the base kept moving: <base> moved again after N pass(es) …`, worktree and branch kept. With `remerge_rounds = 0` a branch whose base moved blocks at once. A pass that finds a conflict goes to conflict rounds. `--dry-run` says `gates rerun on its merge if its base moves`; the passes make no model calls themselves, but a red merge goes to a fix loop whose review rounds restart at zero, so the `--budget-total` estimate counts, per pass (`remerge_rounds`), the review and its fix rounds for a reviewed tier (the verify fix rounds are shared, counted under `verify_rounds`). It leaves out a fix call that uses no round: a verify worker answering `outside:` and a prove waiver.
  - **Conflict rounds.** A branch that won't merge cleanly into its base (or a companion's trunk), because the base moved while it was worked, goes back to its worker before it blocks, up to `conflict_rounds` times (`.ergon.toml`, default 1; 0 blocks at once for a hand merge, as before). Dispatch checks with `git merge-tree` after the gate passes, outside the state lock, and again under the lock just before it merges. On a conflict it resumes the worker's session (or starts a fresh one, by the same rules as fix rounds) with each conflicted repo's base, the base's tip, the conflicted files and the base's commits since the fork (`git log --oneline <fork>..<base>`). **The worker's contract:** in each conflicted worktree, `git merge <base>`, resolve only the conflicted hunks so that both sides' intent survives, and commit the merge citing the task ID (in a companion with `forbid_tracker_ids`, a message with no ID, since git's default names the `task/<ID>` branch). No rebase, no reset or force-move of the branch, nothing unrelated. A worker that can't reconcile the two sides ends with `QUESTION:` lines and `RESULT: asking`, or `RESULT: blocked — <why>` (which files a human task, as any worker block does).
    - **The checks** after it says done, per conflicted repo: the worktree is clean (no merge under way, no tracked changes), the branch tip is a merge commit with a parent on the base at or past the tip the worker was given, no line starting `<<<<<<< ` or `>>>>>>> ` is left in a file the branch changes from the base, and `git merge-tree` now merges cleanly. A miss blocks the task with that reason (no human task; worktree and branch kept). Then the done checks, verify and review run again on the new tip, since the resolution is new code; their verify and review fix rounds count on their own, apart from the conflict rounds.
    - **What the worker is shown of the other side.** Besides the base's commit subjects, the prompt lists the tasks that landed on the base since the fork (tracker IDs cited in `fork..base` commits; for a companion with `forbid_tracker_ids`, the `landed` history rows whose `companions` tip is in that range): each one's title, `## What` and `## Done when`, quoted line by line after `| ` so task text can't pass for the prompt's own structure, each section cut at `CONFLICT_SECTION_MAX` characters, at most `CONFLICT_TASKS_MAX` tasks and then a count of the rest. The worker must keep each listed Done when true after the merge, and ask (`RESULT: asking`) if both sides can't hold. The review that follows the round gets the same list and fails a resolution that drops one.
    - If the base moves again and the branch conflicts again (before the lock, or under it, when another task landed meanwhile), another round runs while `conflict_rounds` allows. Rounds out (or a Ctrl-C, or the `--budget-total` cap, as for fix rounds): the task blocks with the last conflict first, why no round followed, every earlier round's conflict, and `merge by hand`. A landed task's Notes say `resolved a conflict with <base> in <files>` for each round. `--dry-run` says `up to N conflict round(s) if its branch conflicts`, and the `--budget-total` estimate counts, per conflict round, a worker plus the verify fix rounds and the review (with its fix rounds) that rerun after it. A conflict round's worker log is `<ID>-<time>-fix<N>.json`, like a fix round's.
- **Anything else is `blocked`,** with a line in `## Notes` giving the reason, the log in `<state>/runs/`, and the `claude --resume <session>` to inspect it. The worktrees and branches stay. Fix it (or merge by hand and set it `done`), or move it back to `ready`; the next dispatch reuses the branches and tells the worker an earlier attempt exists. If a companion merge landed but a later merge failed, the note says which landed.
- **Skipped:** `human` tasks (listed at the end as yours), and tasks whose `touches:` include a nested repo, which a worktree doesn't contain. Work those interactively.
- **Overlap.** A task whose `touches:` share a path with a running one is held, not started, until that one lands or blocks, so the second never conflicts with the first. Two entries are shared when equal or when one is a parent directory of the other, split on `/` (`ergon` matches `ergon/gates.py`, not `ergonx/a.py`); companion names themselves don't count. A task with an empty or missing `touches:` overlaps every other task: it waits for all running ones and nothing launches beside it (recorded as held with `touches` `["(none declared)"]`). `--dry-run` prints `held  T-2 behind T-1` for these (`no touches: declared` for the empty case), and `overlap` for a shared path with a task already `doing` elsewhere.
  - **Opt-in `overlap` (T-197).** `.ergon.toml` `overlap` (integer, default 1; `ergon check` refuses below 1 or a non-integer) is how many running tasks may share a path. At 1 nothing changes. Above 1, a ready task launches beside running tasks it shares paths with while fewer than `overlap` of them run, and it relies on the merge gates (**Merge passes**, `remerge_rounds`): whichever lands second has the moved base merged in and its gates rerun. Held whatever `overlap` is: either task has no `touches:`, a shared path falls under a gate file (`[gates] protect`, `.ergon.toml`) or the `repros` directory, or the tasks have different bases (different epics, or one in none). The `held` row's `why` says which. `--dry-run` prints `beside  T-2 with T-1: both touch <paths> (overlap = N)` for tasks that may run together and keeps `held` for the rest. The `dispatched` row gets `beside` (the running task ids it shares paths with) and `beside_touches` (the shared paths) when it launches beside any.
  - **By component (opt-in, T-144).** `hold_by = "component"` in `.ergon.toml` (default `"touches"`; it needs a `concepts` map) holds two tasks whose `touches:` overlap apart only when they also share a component in their `concepts:` tags. Overlapping tasks about different components run side by side and don't count toward `overlap`: the launch line says `(beside T-1: touches overlap, no shared component)`, the `dispatched` row lists them under `beside` and `beside_touches`, and `--dry-run` prints `hold_by    component` and `beside  T-2 with T-1: …, but they share no component`. The cases `overlap` always holds (no `touches:`, a gate file or `repros` path, different bases) still hold. A shared path can still conflict textually; whichever lands second gets the merge passes and conflict rounds (`conflict_rounds`). Only current tags count: a task whose `tagged:` stamp is stale (its brief changed, or a tag left the map), whose tags were written by hand with no stamp, or whose tags are empty shares every component; run `ergon tag` first. A `held` row then also says `components` (the shared ones) or `untagged` (whose tags aren't known). The map is read once a run; `check` fails an unknown `hold_by` value or `"component"` without a map, and dispatch refuses to start on one, or on a map that doesn't hold.
- Dependencies chain within one run: when a task lands, anything that was waiting on it gets picked up.

## Web board: `ergon serve`

`ergon serve [PATH] [--port N] [--bind 127.0.0.1]` starts a read-only web view of the tracker (standard library only, no assets fetched). Pages: `/` the board (open work by status and tier, epics with progress, what waits on a human, live `doing` state), `/review` (what to read before approving: proposed epics with their Goal, Out of scope and Constraints and the command to approve them, then proposed tasks grouped by `depends:` (linked chains together in dependency order, each group with its own approve command; unlinked tasks under "Independent" by tier), a dependency map per epic (then one for tasks with no epic), a card per task with What and Done when, findings from files such as missing `file:line` citations or touches, empty Done when / `tier_why` / touches and dead depends, a multiple-choice quiz scored in the page, and the approve command to copy; the page approves nothing), `/metrics` (stats, review, latency, trust pyramid, tokens; `?epic=&since=&until=`), `/e/E-NNN` (the epic's journal entry, then its replay timeline), `/t/T-NNN` (a task's brief, history, runs and `claude --resume` commands, and with a concept map the tasks it relates to), `/runs/NAME` (one raw file from `<state>/runs/`). It only answers GET and HEAD, writes nothing, runs no git and launches no claude. Task text is escaped; the Host header must be `localhost` or an IP literal.

Several projects: each `ergon serve` process serves one project, the one around PATH (default: the cwd's). With no `--port` it takes the first free port from 4300 up (4301, 4302, ..., up to 4399) and prints `ergon serve: http://127.0.0.1:4301/  (<project>, read-only; ...)`, so `ergon serve ~/code/a` and then `ergon serve ~/code/b` just work. Ports follow the start order, so bookmarks can move: pass `--port N` for a fixed one (a taken `--port` is an error, never moved). Every page names its project in the title and the header.

Options: `/review` and `/t/T-NNN` show a task's `## Options` as a numbered list with none recommended (a lens section shows its crux and fields in lens order; every chosen lens is marked with who and when), with an `ergon choose T-NNN <lens>` command per lens, one for a combination and one for `--own` while nothing is chosen (`ergon choose T-NNN N` per option on a numbered list), and none once chosen. `/review`'s approve command leaves out tasks with options and no choice (listed as "choose first"), findings flag a proposed feature with no options or no choice, and the board counts and lists "awaiting choice". Serve takes no input.

The quiz comes from `ergon quiz [--all] [--per 2] [--model sonnet] [--budget USD]`, since serve can't launch claude. It runs one `claude -p` with no tools over the proposed briefs and writes `<state>/runs/quiz/quiz-<time>.json`. Each question carries its task ID and a hash of that task's brief, and `/review` hides it once the task changes or stops being `proposed`. A second run keeps the questions that are still current and asks only about tasks without one. It's safe for agents to run (it writes only that file), but it costs a sonnet call.

The epic journal comes from `ergon journal [E-NNN ...] [--all] [--model sonnet] [--budget USD]`, for the same reason. One `claude -p` per epic (no tools, empty folder) gets the epic's Goal / Out of scope / Constraints, its tasks, its history rows and the commits citing them, and writes `<state>/runs/journal/E-NNN-<time>.json` (`{generated, model, cost, epic, body}`; the newest wins, older ones stay). No IDs: epics with no entry or newer history rows; `--all`: every epic. `/e/E-NNN` shows the newest entry (escaped) above the timeline, or `no journal entry yet: ergon journal E-NNN`. Finishing an epic writes its entry too, after the state lock is released, unless `journal = false` in `.ergon.toml`; a failing `claude` only warns.

**There is no login.** It listens on loopback by default. Any other `--bind` prints a warning: anyone who can reach that address reads every task brief, run log, cost and session ID. Bind only an interface you trust (a tailnet IP), never a public or shared network. Agents don't need it; it's for humans watching dispatch.

## History: `<state>/runs/history.jsonl`

One JSON object per line, appended as things happen, gitignored with `runs/`. Every row has `at` (ISO-8601 local time with offset, to the second), `task` (`T-NNN`, or null for an epic's own events), `epic` (`E-NNN` or null) and `event`. Paths (`log`, `worktree`) are relative to the main checkout. Each row is one `write()` on an `O_APPEND` descriptor under an `flock` on the file itself, so parallel workers, dispatch runs and terminals never interleave rows. A row that can't be written prints a warning; the command goes on. Rows are never rewritten, and fields are only ever added: a reader skips events and fields it doesn't know. `ergon stats` still counts from the run files, so runs from before the history count too. It's a record, not a gate, with one exception that only narrows: the weakening check counts a `touches:` entry, a `harden:` id or a `suppress_ok:` file only if an `approved` (or the first `dispatched`) row since the last approval recorded it. The guard refuses agent edits and shell writes to `runs/`, so a worker can't forge a round or a verdict by tool call, but like every guard that's a speed bump: anything that can write to `runs/` could append a row, so an `approved` row is no proof of approval (the task file's `approved:` stamp and the commits are).

| `blocked` | the task went `blocked`, from dispatch or a failed `accept` | `reason`, `log`, `session`, `asked` (the worker itself said blocked) |
| `closed` | `close` | `by`, `as`, `reason` |
| `status` | `set` changed a task's or epic's status: work moved by hand or by an interactive agent, outside dispatch (dispatch and the human gates record their own events, never this one) | `from`, `to`, `by` (git `user.name`), `agent` (true if run in an agent shell, `CLAUDECODE` or `AI_AGENT` set; a hint, not proof) |
| `window` | a dispatch run ended and both probes read the 5-hour window (`task` and `epic` are null) | `before`, `after` (utilization, 0..1), `resets_at` (epoch seconds), `cost` (the run's workers, reviewers and probes, USD), `same` (false if the window reset in between: no rate from it) |
| `epic_finished` | the epic merged into the trunk and closed (`task` is null) | `branch`, `commit` (the merge commit; both null if it never had a branch) |
| `graded` | `ergon grade` wrote cost-of-delay grades (`task` is null) | `tasks` (the IDs it wrote), `model`, `cost`, `dropped` (comparison replies it threw away) |
| `filled` | `ergon fill` wrote blank parts of proposed briefs (`task` is null) | `tasks` ({ID: [parts written]}), `model`, `cost`, `dropped` (reply entries for tasks it wasn't asked about) |
| `tagged` | `ergon tag` wrote `concepts:` from the concept map (`task` is null) | `tasks` ({ID: [component ids written]}), `model`, `cost`, `dropped` (reply entries it threw away: ids not in the map, tasks it wasn't asked about, malformed answers) |
| `learned` | `ergon learn` asked claude, from the CLI or dispatch (`task` is null) | `by`: `learn` / `dispatch`, `model`, `cost`, `ok` (the reply parsed), `asked` (the incident ids sent), `filed` (the IDs it proposed), `joined` (task ID → incident ids added to its `harden:`), `refused` and `dropped` (counts: classes refused, incident ids in the reply it threw away), `record` |
| `pinned` | `ergon pin` set or cleared a task's `pin:` (human only) | `by`, `pin`: `first`, `last`, or null on a clear |

`round` (2, 3, …) is on the `dispatched`, `resumed`, `worker_end`, `verify` and `review` rows of a fix round (review round N+1 is fix round N), of an `--until-done` round (its worker rows carry `after: "until_done"`), and on the `conflict` row, the worker rows of the conflict round that follows it and the verify and review rows after that. It numbers worker runs on the branch in order, whatever the kind of round. A row without `round` is round 1. Other loops are to mark their rounds the same way.
